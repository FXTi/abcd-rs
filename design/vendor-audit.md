# Vendor audit — upstream code we actually use

Status: **second full pass complete** (every vendored upstream file + both
bridge files read line by line, no agents). This document records what each
piece of upstream code does, how the integration works, every defect found,
and the compatibility/architecture decisions derived from the audit.

## 1. Integration model (answering "how are we integrated?")

- Both `-sys` crates compile vendored C++ **into the same binary** as the
  Rust code: `cc::Build` produces a static archive (`libisa_bridge.a` /
  `libfile_bridge.a`) linked into the final test binary / library. There is
  **no separate .so/.dylib and no dlopen**; C++ runs in the same process.
- C++ exceptions never cross the boundary: every bridge entry point is
  wrapped in `try { ... } catch (...)` and converts failures to sentinels
  (review finding #8). Two C++ `abort()` paths remain reachable on
  malformed input (see findings #A4/#A5) and are mitigated at the bridge.
- abcd-file-sys bindgen, two passes: (1) pure-C `bridge/file_bridge.h`
  (opaque `Abc*` types) for the function surface; (2) `file_bridge_enums.h`
  (generated by build.rs) for vendor enum constants — values always come
  from the vendor headers, names are listed by us.
- abcd-isa-sys: bindgen only over `bridge/isa_bridge.h`; the Rust `Bytecode`
  enum is **generated from isa.yaml** by gen.rb (not parsed from C++).
- Upstream changes enter only through the explicit vendor sync
  (zero-diff + sha256 metadata) plus a rebuild; generated code is snapshotted
  into OUT_DIR; the bridge is the stable C ABI boundary. Local adaptation
  lives exclusively in `bridge/` and `bridge/shim/` (never in `vendor/`).
- Missing upstream implementation units are provided by the bridge:
  file.cpp's File methods, GetFileType, ContainsLiteralArrayInHeader,
  timers.cpp's two static members; shim headers stand in for logger.h,
  securec.h, zlib.h (inline adler32), os/mem.h, os/filesystem.h.

## 3. Findings log

### A — defects in upstream code (mitigated at the bridge or documented)

- **#A1 (P0, fixed)**: `LiteralDataAccessor::EnumerateLiteralVals` has no
  `TAGVALUE (0x00)` case → `UNREACHABLE()` abort. modules.abc (12.0.6.0)
  contains literal arrays whose items start with 0x00 → decode aborts in
  `decode_literal_arrays` after all 2035 classes parse. All upstream
  releases (3.2 → master) share the code; the 4.0-era es2panda emitter
  proves 12.0.6.0 files use [tag][value] pairs with TAGVALUE meaning a
  1-byte INTEGER_8. Fix: replace the bridge's vendor call with our own
  bounded, tolerant enumerator (TAGVALUE → 1-byte value, unknown tag →
  stop) — no vendor patch.
- **#A2 (P1, fixed)**: For versions > 12.0.6.0 (24.0.0.0) the header's
  `num_literalarrays`/`literalarray_idx_off` are INVALID and the array
  table lives elsewhere (upstream `GetLiteralArraysId` in file.cpp, which
  we do not compile). Our bridge returns 0xFFFFFFFF for the count → a
  naive Rust loop would run 4 billion iterations. Fix: return 0 for
  INVALID_INDEX and implement the 24-entry path (or explicitly reject
  until implemented — must be deterministic, never a huge loop).
- **#A3 (P1, fixed)**: murmur3 / PseudoFnv hash 4-byte blocks and
  `ReadULeb128`/`ReadLeb128` 5-byte reads are unbounded; `abc_file_open`
  maps the caller's Rust buffer directly with no trailing padding, so a
  string item ending at the file end can read past the heap buffer. Fix:
  `abc_file_open` copies into a buffer with NUL padding.
- **#A4 (P1, mitigated)**: `LOG(FATAL, PANDAFILE)` sites in compiled vendor
  code (`line_number_program.h` RESTART_LOCAL, `debug_info_extractor.cpp`
  unknown END_LOCAL) would abort upstream; our logger shim degrades them to
  stderr output. Intentional, but fragile: a future shim change or vendor
  sync adding a new LOG(FATAL) site would re-arm the abort.
- **#A5 (P2)**: `AddIndexDependecies` calls `std::abort()` when an item's
  index dependencies overflow two 16-bit index headers (giant classes).
  Documented; not reachable for normal inputs.
- **#A6 (P2)**: `ReadULeb128`/`ReadLeb128`/`SkipULeb128` may read past a
  short span (5-byte encodings; SkipULeb128 silently drops a byte). The
  span's `Read` has bounds checks, the LEB128 helpers do not. Call sites
  are inside file_size, so reads stay in the mapped buffer, but they are
  still out-of-span reads.
- **#A7 (P1, format fact)**: API ≥ 12 does not emit ProtoItem and methods
  store `proto_idx = INVALID_INDEX_16`; method signatures (return/arg
  types) are **not present in the file at all**. Verified: files built by
  our builder decode with `return_type=None`. This is upstream format
  behavior (es2abc 12.x output matches). Consequence for our round-trip:
  signatures cannot be recovered from 12+/24 files; the Rust model keeps
  them `Option` and encode cannot restore them. (Decision B includes
  verifying 9/11 files, which do carry protos.)
- **#A8 (P2, fixed)**: MemoryWriter does no checksum counting → our output files
  have checksum 0 (upstream FileWriter computes adler32). Fix plan:
  patch the checksum after write in the bridge finalize.
- **#A9 (P2)**: upstream copy-paste defects (GetAnnotationsNumber counts
  runtime; field type-annotation enumerators match ANNOTATION; GetNumArgs
  underflow; IndexAccessor::GetOffsetById unbounded) — bridge-level fixes
  planned where the Rust side consumes them.

### B — defects in our bridge/Rust adaptation (found by this audit)

- **#B1 (P1, fixed)**: `component_type_from_tag` (bridge) maps 'W'/'X' to F32/F64
  — wrong; upstream is 'T'=F32, 'U'=F64. Simultaneously
  `encode.rs::is_entity_array_tag` treats 'T'/'U' as entity arrays —
  wrong; entity arrays are 'V'/'W'/'X'/'Y'/'Z'/'@'. Both bugs are masked
  today only because every involved element is 4 bytes wide. Fix both +
  regression test.
- **#B2 (P1, fixed)**: `abc_index_get_offset_by_id` exposes the unbounded vendor
  accessor. Add a bounds check against the index header size.
- **#B3 (P2, fixed)**: `abc_proto_num_args`/`abc_proto_get_arg_type` forward the
  vendor `GetNumArgs` underflow. Clamp in the bridge.
- **#B4 (P2, fixed)**: `abc_method_handle_read` decodes ULEB with no 5-byte bound.
- **#B5 (informational)**: class descriptors read through
  `abc_file_get_string_utf16` rely on the class-item name ULEB having no
  ascii bit — utf16 length decodes correctly by coincidence; strlen drives
  the conversion, so the value is only used for buffer sizing (safe).

| 12(beta1) | 12.0.2.0 | yes | **current default** | GetVersionByApi hardcode |
| 0/24 | 24.0.0.0 | **must** | yes (target) | second-gen final; literal arrays via index path (#A2) |
| static marker | {0,1,0,7} | detect only | no | STATIC_VERSION |

Third generation (`static_core`, file version 0.1.x) is out of scope for
Phase 1: separate directory tree, separate format, still in flux. The
architecture below leaves a slot for it without touching the core model.

## 5. Architecture decision — single core model + FormatProfile

Derived from the audit and aligned with the "one core data type, upstream
definitions referenced, upstream churn does not affect us" goal:

1. **Single core model** — `abcd_file`'s Rust model + `abcd-ir`. No
   version branches inside the core; `File.version` is metadata only.
2. **Upstream definitions are referenced, not copied** — enum values
   (LiteralTag / FunctionKind / SourceLang / Type::TypeId / ACC_*) via
   bindgen from vendor headers; `Bytecode`/formats/flags generated from
   isa.yaml. Version tables (`api_version_map`, `ContainsLiteralArrayInHeader`,
   STATIC_VERSION) are already exposed by the bridge.
3. **A `FormatProfile` layer carries all compatibility work** — decode
   consults capabilities by header version (literal-array table in header
   vs index path, proto presence, field-type encoding mode, tag-stream
   differences); encode consults the target API. Every difference found in
   §4 becomes a profile capability. Legacy quirks (#A1, #A6, upstream
   copy-paste bugs) are absorbed here or in the bridge, never in the core.
4. **Upstream churn containment** — vendor zero-diff sync + sha256
   metadata; local adaptation only in bridge/shim; generated code in
   OUT_DIR; the C ABI surface is the stable contract. A future 0.1.x
   backend = a second vendor subset + a second profile, same IR.

## 6. Hermes comparison

Hermes (reference tree `hermes-main/`) confirms the same two-layer shape:

- Hermes **IR** (include/hermes/IR: Instrs.def macro table, IR.h,
  IRBuilder, IRVerifier, CFG) is pure C++ and knows nothing about the HBC
  format; **BCGen/HBC** (BytecodeList.def opcode table) is the format
  backend reached through Lowering. We mirror this exactly: `abcd-ir`
  (arena model, Braun SSA, InstData ~70 variants, verify.rs) is the core;
  `abcd-file` + `-sys` is the format backend.
- Differences that are ours by necessity: Hermes serves a single engine
  with one bytecode version; we serve a frozen format family across four
  file versions, hence the FormatProfile layer (no Hermes analogue). We do
  not port Hermes's Lowering/RegAlloc — Phase 1 requires semantic
  fidelity, not register rearrangement.
- Direct borrows already in place: table-driven instruction definitions
  (isa.yaml/Instrs.def), IR verification, CFG utilities. Candidate future
  borrows: an IR-level verifier run in CI on decoded real files.
